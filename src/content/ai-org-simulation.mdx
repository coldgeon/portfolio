## 문제 해결

<CaseStudy number="01" title="Cloud Run에서 멈춘 시뮬레이션, 로그에서 원인을 찾다">

### 문제

Shadow Roleplay 실행 중 백엔드가 512MiB 메모리 제한을 초과하면서 스트림 진행이 멈추는 문제가 있었습니다.

### 판단

모델 응답만 살피는 것으로는 부족했습니다. Cloud Logging과 실행 환경을 함께 확인해 메모리와 동시 실행 조건을 조정해야 했습니다.

### 구현

백엔드 메모리를 1GiB로 조정하고, 실행할 때마다 의존성을 동기화하던 `uv sync`를 Docker 시작 명령에서 제거했습니다. 장시간 스트림 요청이 겹치는 부담을 줄이도록 동시 실행 수도 낮췄습니다.

### 결과와 근거

Cloud Run 배포 설정과 Docker 실행 방식을 변경했습니다. 실제 로그에서 전체 데모 흐름이 4회 이상 실행된 기록을 확인했고, API 지연 시간도 단계별로 정리했습니다.

</CaseStudy>

<CaseStudy number="02" title="AI 호출의 대기 시간과 세션 관리 한계 확인">

### 문제

요구사항 분석과 역할 시뮬레이션에 100초 이상 걸리는 사례가 있었습니다. 프로토타입의 세션은 인메모리 방식이어서 여러 인스턴스로 확장할 때 상태 유실 가능성도 있었습니다.

### 판단과 관찰

요구사항 분석은 약 119~189초, 시뮬레이션은 약 99~136초가 관찰됐습니다. 이 수치는 지연 시간의 관찰값이며 개선 성과를 뜻하지 않습니다.

### 대응과 후속 과제

실행 로그를 통해 한계를 문서화했습니다. 비동기 작업 처리, 진행 상태 이벤트, 단계별 타임아웃과 재시도, 세션 영속화를 후속 개선 과제로 정리했습니다. 이 기능들은 이번 프로토타입의 구현 성과에 포함하지 않습니다.

</CaseStudy>

## 협업과 담당 범위

백엔드·인프라를 담당해 프론트엔드에서 PDF를 입력하면 에이전트 실행과 보고서까지 이어지도록 연결했습니다. 모델을 호출하는 환경, 세션 API와 배포 환경을 함께 구성했습니다.

## 배운 점과 다음 개선

AI 서비스를 연결하려면 모델 호출뿐 아니라 상태 관리, 대기 시간과 관측 가능성도 설계해야 했습니다. 모의 실행과 실제 실행을 분리하는 일, 시연 후 클라우드 리소스를 정리하는 일도 개발의 일부로 경험했습니다.
