## 유지보수 사례

<CaseStudy number="01" title="토큰 저장·갱신과 새로고침 인증 복원">

**문제** · 메모리 액세스 토큰은 새로고침 시 사라졌고, 관리자 진입에서 403 응답이 발생했습니다.

**판단·수정** · 액세스 토큰은 메모리, 리프레시 토큰은 HttpOnly 쿠키에 두도록 연결했습니다. Spring Boot 로그인·갱신 API와 JPA RefreshToken 엔티티·저장소를 수정해 갱신 시 기존 토큰을 교체하는 RTR을 구현했습니다.

**확인** · 작업 기록의 새로고침 후 인증 복원과 본인 커밋의 401/403 처리·JSON이 아닌 응답 처리·보호 경로 수정이 근거입니다. 토큰 누락·만료·재사용 분기는 코드에서 확인했으며, 모든 예외 상황의 실행 테스트를 완료했다고 표현하지 않습니다.

**효과** · 관리자 화면의 인증 상태와 백엔드 갱신 흐름을 함께 관리할 수 있도록 보완했습니다. 서비스 전체의 보안 완성을 의미하지 않습니다.

</CaseStudy>

<CaseStudy number="02" title="새 관리자 화면을 기존 API·배포 경로에 통합">

**문제** · 새 관리자 화면을 기존 공지 API와 온프레미스 환경에 연결해야 했습니다.

**판단·수정** · Vite·JavaScript 화면에서 기존 API를 연동하고, 로그인·갱신·로그아웃은 백엔드도 직접 수정했습니다. 프론트 빌드를 Spring Boot의 /admin에 포함하고 SPA 진입·정적 파일 경로를 보완해 기존 Nginx 배포 구성에 연결했습니다.

**확인·효과** · 관리자 진입 경로의 컨트롤러·정적 리소스 처리와 API 연동 커밋을 확인했습니다. 별도 프론트 호스팅을 추가하지 않고 기존 배포 흐름에서 기능을 제공했습니다.

</CaseStudy>

<CaseStudy number="03" title="기존 알림 식별자 처리에 암호화 적용">

**대상·수정** · 기존 앱의 device_id·FCM token 처리에 RSA·AES 하이브리드 암호화를 적용했습니다. 관리자 로그인 토큰과 구분한 유지보수 작업입니다.

**범위** · 암호화 적용 기록을 근거로 소개하며, 서비스 전체 보안 검증이나 성능 개선 수치를 주장하지 않습니다.

</CaseStudy>

<details className="content-details">
<summary>화면·코드 증빙의 범위</summary>

상단 앱 이미지는 팀 서비스 소개 자료입니다. 관리자 인증·배포 수정은 본인 커밋과 개인 작업 기록으로 확인했습니다. 저장소가 비공개이므로 공개 링크나 원본 코드를 게시하지 않습니다.

</details>

## 배운 점

기존 서비스의 유지보수에서는 API 계약, 인증 상태와 정적 파일·배포 경로를 함께 확인해야 합니다.
