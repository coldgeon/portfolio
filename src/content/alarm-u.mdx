## 문제 해결

<CaseStudy number="01" title="노출될 수 있는 알림 식별자를 보호하기">

### 배경

로그인 기능이 없는 기존 알림 서비스에서 device_id와 FCM token을 다루는 백엔드 유지보수를 맡았습니다. 알림 수신에 필요한 식별자가 그대로 노출될 수 있는 상태를 확인했습니다.

### 판단

기능을 유지하는 데 그치지 않고, 식별자 보호를 변경 범위에 포함해야 했습니다. 서비스 간 안전한 전달과 서버 측 처리에 모두 적용할 수 있는 방식을 검토했습니다.

### 구현

device_id와 FCM token 처리에 RSA와 AES를 결합한 하이브리드 암호화를 적용했습니다. 기존 흐름을 먼저 파악한 뒤, 암호화가 필요한 구간과 변경 범위를 정리하며 구현했습니다.

### 결과와 근거

암호화를 적용한 유지보수 기록을 남겼습니다. 보안 강도나 성능 수치는 검증 자료가 확보된 뒤 공개하기로 하고, 이번 경험에서는 데이터 보호와 운영 검증을 함께 고려하는 기준을 세웠습니다.

<CaseStudy number="02" title="관리자 기능과 배포 흐름을 하나로 연결하기">

### 배경

관리자 기능을 추가하면서 화면 구현과 백엔드 연동뿐 아니라, 기존 온프레미스·Nginx 환경에서 어떤 배포 흐름을 유지할지 함께 고려해야 했습니다.

### 판단

관리자 프론트엔드를 별도 서비스로 배포하면 운영 지점이 늘어날 수 있었습니다. 기존 백엔드 배포 흐름에 맞춰 프론트엔드 빌드 결과를 통합하는 구성을 선택했습니다.

### 구현

관리자 페이지를 구현하고 백엔드와 연결했습니다. 프론트엔드 빌드 결과를 백엔드 프로젝트에 통합해 함께 배포하는 구성을 적용하고, 온프레미스·Nginx 환경의 서비스 제공 흐름을 확인했습니다.

### 결과와 근거

관리자 기능과 통합 배포 구성을 프로젝트 기록으로 남겼습니다. 화면과 API가 연결된 뒤에도 실제 서비스가 제공되는 환경과 운영 단계를 함께 살펴봐야 한다는 점을 배웠습니다.

</CaseStudy>

## 협업과 담당 범위

기존 서비스의 백엔드 유지보수와 관리자 기능을 맡았습니다. 신규 개발과 달리 이미 운영 중인 서비스의 구조와 배포 환경을 먼저 이해한 뒤, 보안·관리 기능의 변경 범위를 정하고 구현했습니다.
