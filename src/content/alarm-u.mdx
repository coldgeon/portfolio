## 문제 해결

<CaseStudy number="01" title="토큰 저장 위치에서 시작해 인증의 전체 흐름을 다시 설계하기">

### 문제

과거 해커톤에서는 제한된 시간 안에 기능을 완성하기 위해 액세스 토큰을 로컬스토리지에 저장했습니다. 실제 사용자가 있는 AlarmIT(AlarmU)의 관리자 기능을 맡으면서, 이전 방식을 그대로 적용해도 되는지 검토했습니다. JavaScript가 접근할 수 있는 로컬스토리지에 토큰을 남기는 방식의 위험을 확인했습니다.

### 판단

액세스 토큰은 브라우저 메모리에 보관하기로 했습니다. 하지만 메모리의 토큰은 새로고침하면 사라집니다. 토큰의 저장 위치와 함께 발급·갱신·인증 복원 흐름을 설계해야 했습니다.

### 구현

- 액세스 토큰은 브라우저 메모리에 보관했습니다.
- 리프레시 토큰은 JavaScript에서 직접 읽을 수 없는 HttpOnly 쿠키에 저장했습니다.
- 새로고침 이후에는 리프레시 토큰으로 액세스 토큰을 재발급받아 인증 상태를 복원하도록 구성했습니다.
- 갱신할 때 리프레시 토큰도 교체하는 RTR(Refresh Token Rotation)을 적용했습니다.

### 구현 결과

액세스 토큰을 로컬스토리지에 남기지 않으면서 새로고침 후 인증 상태를 복원할 수 있도록 구현했습니다. 저장 위치를 바꾸는 결정이 갱신 API와 사용자 경험까지 이어진다는 점을 배웠습니다.

HttpOnly는 쿠키를 JavaScript에서 직접 읽지 못하게 하는 속성입니다. 토큰의 직접적인 읽기를 제한하지만, XSS 자체를 방지하는 기능은 아닙니다.

</CaseStudy>

<CaseStudy number="02" title="관리자 화면을 기존 API와 운영 환경에 연결하기">

### 배경

관리자 기능은 이미 운영 중인 서비스에 추가하는 작업이었습니다. 화면과 API뿐 아니라 기존 온프레미스·Nginx 배포 환경을 함께 이해해야 했습니다.

### 판단

관리자 프론트엔드를 별도 서비스로 배포하면 운영 지점이 늘어날 수 있었습니다. 기존 백엔드 배포 흐름에 맞춰 프론트엔드 빌드 결과물을 통합하는 구성을 선택했습니다.

### 구현

Vite와 JavaScript로 관리자 화면을 만들고 기존 Spring Boot API에 연결했습니다. 프론트엔드 빌드 결과물을 백엔드 프로젝트에 포함해 온프레미스·Nginx 환경에서 함께 제공하도록 구성했습니다.

### 구현 결과

관리자 화면과 API를 연결하고, 기존 서비스의 배포 흐름 안에서 제공하는 구성을 구현했습니다. 새 기능을 만드는 것에서 그치지 않고 실제로 서비스가 제공되는 환경까지 고려했습니다.

</CaseStudy>

<CaseStudy number="03" title="기존 알림 식별자의 보호 범위를 확인하기">

### 배경과 구현

관리자 인증과 별도로, 기존 알림 서비스의 백엔드 유지보수에서 device_id와 FCM token을 다뤘습니다. 노출될 수 있는 식별자의 처리 흐름을 파악하고 RSA·AES 하이브리드 암호화를 적용했습니다.

### 담당 범위

이 작업은 알림 식별자 보호를 위한 유지보수입니다. 관리자 로그인 토큰의 보관·갱신 구조와 구분해 변경 범위를 정리했습니다.

</CaseStudy>

## 협업과 담당 범위

기존 서비스의 백엔드 유지보수와 관리자 기능을 맡았습니다. 익숙한 구현 방식을 다시 검토하고, 화면·API·배포 환경의 연결을 고려해 변경 범위를 정했습니다.
