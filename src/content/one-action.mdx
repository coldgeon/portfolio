## 실행 환경과 연결 검증

<CaseStudy number="01" title="IAM 403을 보완한 뒤 외부 HTTP 응답 확인">

**문제** · 앱이 실행되어도 외부에서 접속할 수 없었습니다. 동료가 Ingress의 보안그룹 생성 권한 오류(403)를 진단했습니다.

**판단·조치** · 리소스 생성 권한의 조건을 보완해야 한다고 판단해 IAM 조건을 수정하고 지정 범위의 허용·거부를 검사했습니다.

**검증·팀 효과** · ALB 생성과 외부 HTTP 200을 확인하고 접근 방법을 공유해 팀이 실제 앱·API 연동을 진행할 수 있도록 했습니다.

</CaseStudy>

<CaseStudy number="02" title="EBS 저장소를 연결하고 Pod 교체 후 파일 보존 확인">

**문제** · 운영 도구를 함께 올릴 용량과 Pod 교체에도 남는 저장 공간이 필요했습니다.

**판단·조치** · EKS 노드를 2→3대로 확장하고 EBS CSI·gp3 저장소를 구성했습니다. 실행 공간과 파일 보존을 나눠 점검했습니다.

**검증·팀 효과** · 3노드 Ready와 시험 Pod 교체 후 파일 보존을 확인했습니다. 동료가 모니터링 기능을 설치할 실행 기반을 제공했습니다. 백업·다른 가용영역 복구 시험은 수행하지 않았습니다.

</CaseStudy>

<CaseStudy number="03" title="실패한 HTTPS 경로를 수정해 로컬 알림 연결">

**문제** · 로컬 환경에서 EKS 내부 주소에 접근할 수 없었고 첫 HTTPS 경로는 503으로 실패했습니다.

**판단·조치** · 외부 진입점과 내부 API 연결을 나눠 API Gateway → VPC Link → 내부 ALB 경로로 수정했습니다. 토큰 적용 도구와 인증·경로 검사를 구성했습니다.

**검증·팀 효과** · 수정 경로를 검사한 뒤 동료가 실제 로컬 알림 수신을 확인했습니다. 저는 통신 경로와 접근 방법을 인계했고, 알림 기능은 팀원이 구현했습니다.

</CaseStudy>

## 협업과 담당 경계

- 초기 사용자 흐름을 제안하고 EKS·GKE 실행 기반·IAM/RBAC·Secret 공급·EBS·환경 연결에 집중했습니다.
- GKE 승격 상태를 기록할 권한이 부족할 때 RBAC을 보완하고 팀원이 실제 승격과 공개 응답을 확인하도록 연결했습니다.
- AI를 구현·검사 보조로 활용했습니다. 작업 범위·권한·비용 판단, 결과 확인과 팀 인계는 직접 수행했습니다.

최종 AI 검토는 AWS 배포 명세 하나를 대상으로 했고 공통 이미지를 세 환경에 배포했습니다. 환경별 독립 AI 검토는 후속 범위입니다. AI 판단·API·CI/CD·모니터링은 팀 서비스의 공동 결과입니다.
