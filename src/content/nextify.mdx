## 문제 해결

<CaseStudy number="01" title="반복 작업과 맥락 판단을 하나의 구조로 나누기">

### 문제

수작업은 반복 비용이 크고, 범용 Code LLM 방식은 프롬프트와 프로젝트 맥락에 따라 결과 편차가 생겼습니다. React에서 Next.js로 옮길 때는 한 파일의 수정이 라우팅, Provider, 브라우저 API와 환경 설정의 연쇄 변경으로 이어졌습니다.

### 판단

모든 작업을 AI에 맡기기보다 반복 가능한 구조 변환, 프로젝트 맥락이 필요한 판단, 자동화하기 어려운 충돌을 서로 다른 방식으로 처리해야 한다고 판단했습니다.

### 구현

Next.js 실행 구조를 기준으로 Environment, Structure, Routing, Assets, Runtime의 5단계와 86개 세부 작업을 설계했습니다. 규칙 기반 자동화, 프롬프트 제약형 AI, 사용자 개입을 작업 특성에 따라 배치하고 선택 기능인 Advanced, Report, Review를 기본 전환 뒤에 연결했습니다.

### 결과와 근거

변환 순서와 책임이 분명한 파이프라인을 만들었고, CLI에서 기본 전환과 선택 기능을 분리해 사용자가 필요한 기능만 실행할 수 있도록 구성했습니다.

</CaseStudy>

<CaseStudy number="02" title="다음 단계로 넘어가기 전에 오류를 처리하기">

### 문제

초기 프로토타입으로 20개 프로젝트를 마이그레이션했을 때 빌드에 성공한 프로젝트는 2개였습니다. 변환 중 발생한 오류를 남겨둔 채 다음 단계로 넘어가면서 문제가 누적되고 있었습니다.

### 판단

각 단계가 끝날 때 타입체크를 실행하고, 확인한 오류를 처리한 뒤 다음 단계로 넘어가야 최종 결과를 신뢰할 수 있다고 판단했습니다.

### 구현

타입체크를 여러 차례 실행해 오류를 수집하고, 결정론적 규칙으로 처리할 오류와 프로젝트 맥락을 고려해 AI가 처리할 오류를 구분하는 검증기를 개발했습니다. 마지막에는 해결되지 않은 오류 파일을 확인하고 빌드를 검증하도록 구성했습니다.

### 결과와 근거

프로토타입 단계의 20개 프로젝트 중 빌드 성공 수가 2개에서 18개로 늘었습니다. 이후 최종 평가에서는 지원 범위에 맞는 오픈소스 프로젝트 30개 모두 빌드에 성공했습니다.

</CaseStudy>

<CaseStudy number="03" title="한 번의 측정 대신 반복 측정으로 성능을 비교하기">

### 문제

Next.js로 파일 구조가 바뀌었다는 사실만으로는 전환의 효과를 설명하기 어려웠습니다. 실행 환경에 따라 변하는 성능 지표를 한 번의 값으로 비교하는 것도 신뢰하기 어려웠습니다.

### 판단

같은 환경에서 여러 번 측정한 중앙값을 사용하고, 대상 선정 기준과 측정 지표를 공개해야 결과를 재현하고 비교할 수 있다고 판단했습니다.

### 구현

지원 범위 내 GitHub 오픈소스 프로젝트 중 Lighthouse 기준에 해당하는 대상을 선정했습니다. 동일한 네트워크와 기기 조건에서 FCP, LCP, SEO, JavaScript Payload를 3회 측정하고 중앙값을 정리하는 Markdown 보고서 기능을 개발했습니다.

### 결과와 근거

30개 프로젝트 평균 기준으로 FCP 38.3%, LCP 18.7%, SEO 7.6%가 개선됐고 마이그레이션 시간은 78.4% 단축됐습니다. 측정 환경과 개별 결과는 최종 발표 자료에 함께 기록했습니다.

</CaseStudy>

## 협업과 리더십

처음 4명이었던 팀이 3명으로 줄었습니다. 팀원 모두 프론트엔드 경험이 있다는 공통점을 바탕으로, 짧은 해커톤형 서비스보다 1년 동안 기술 문제를 깊이 다루는 방향을 제안했습니다. 빠르게 바뀌는 웹 기술과 반복되는 React → Next.js 전환 작업에 주목해 Nextify로 주제를 전환했습니다.

전체 흐름과 구조를 설계하고 팀의 역할을 조율했습니다. 새로운 아이디어에 대한 긍정적인 피드백을 팀과 공유하고 목표를 구체화해, 인원이 줄어든 뒤에도 다시 개발에 집중할 수 있도록 이끌었습니다.

> 어려운 상황에서 팀을 이끄는 일은 진행 상황을 확인하는 데서 끝나지 않았습니다. 함께 납득할 수 있는 목표를 만들고, 각자의 역할을 연결하는 일이 필요했습니다.

## 배운 점과 다음 개선

기능을 구현하는 일과 결과를 검증하는 일을 하나의 개발 과정으로 보게 되었습니다. 자동화는 모든 판단을 대신하는 것이 아니라 반복 가능한 부분과 맥락이 필요한 부분을 구분하고, 결과를 확인할 수 있을 때 신뢰를 얻는다는 점을 배웠습니다. 다음에는 실패 사례를 데이터로 축적해 지원 범위와 검증 정확도를 더 명확하게 만들고 싶습니다.
